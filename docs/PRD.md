# PRD — 강의실 시험 무결성 플랫폼

- 문서 버전: v1.0 (2026-11-23)
- 작성 방식: 브레인스토밍 → 설계 문서(`docs/superpowers/specs/2026-11-23-exam-integrity-platform-design.md`) → 본 PRD
- 후속 문서: `docs/SPEC.md`(기능별 동작·완료 조건), `docs/STUDY.md`, `docs/RETROSPECTIVE.md`

## 1. 한 줄 요약
강의실에서 노트북으로 치르는 시험에서, **브라우저 이탈과 브라우저 안의 AI 사용 흔적을 실시간으로 감지해 감독관에게 알리고, 감독관이 확인·조치한 과정을 기록으로 남기는** 웹 시험 플랫폼.

## 2. 문제

### 2.1 누구의 어떤 상황인가
- **교수자·조교(감독관)**: 강의실에서 노트북/PC로 시험을 치르게 하면, 수십 명의 화면 안에서 무슨 일이 일어나는지 볼 수 없다. 학생이 다른 탭에서 ChatGPT를 열거나 브라우저 사이드바에서 AI를 켜도, 감독관은 교실 앞에서 그것을 알아챌 방법이 없다.
- **정직한 학생**: 부정행위가 퍼지면 성적의 공정성이 무너진다. 반대로 지나친 자동 처벌(예: 알림 팝업 때문에 포커스가 빠졌는데 자동 종료)은 억울한 피해자를 만든다.

### 2.2 판단 근거 (뉴스·조사)
| 근거 | 내용 | 이 프로젝트에 주는 의미 |
|---|---|---|
| 국내 대학 AI 부정행위 연쇄 보도 (2025.11~) | 연세대 비대면 과목(약 600명) 중간고사에서 생성형 AI 집단 부정행위 적발. 고려대·홍익대·서울시립대·아주대·건국대 등에서 비대면·대면 시험 중 AI 사용, AI 스마트안경 착용 사례 보도 [1][2] | 문제가 실제로, 여러 대학에서, 반복적으로 일어나고 있다 |
| 연세대 사례의 감독 방식 | 시험 중 화면·얼굴 영상을 제출하게 했는데도 집단 부정행위가 발생 [1] | **감시(녹화)만으로는 부족**하다. 신호를 모아 사람이 실시간으로 확인하는 구조가 필요하다 |
| 대면 시험(고사장)으로 확산 | 초소형 카메라로 문제를 외부 전송, 스마트워치로 답을 받은 사례 [3] | 강의실 시험도 안전하지 않다 → **강의실 시험을 대상으로 한 근거** |
| 대학의 대응 한계 | 소수 감독관이 다수 수험생을 관리, 인력·예산 한계, 가이드라인 미비 [4][5] | 감독관에게 **"지금 어디를 봐야 하는지"** 알려주는 도구가 필요하다 |
| 영국 HEPI 학생 조사 (2025) | AI 도구 사용 학생 66% → 92%로 증가. 학생이 꼽은 1위 억제 요인은 "부정행위로 적발될 가능성"(53%) [6] | **"기록되고 있다"는 인식 자체가 억제 장치**다 → 사전 고지, "기록 중" 표시 |
| 미국 대규모 연구 (9.5만 명) | AI를 매일 쓰는 학생일수록 부정행위 비율이 높음. 금지만으로는 해결되지 않는다는 결론 [7] | 완벽 차단이 아니라 **억제 + 증거 + 사람의 판단**으로 접근 |

> 주: 기사마다 날짜·수치가 다르게 보도된 부분이 있어(예: AI 가이드라인 마련 대학 비율 22.9% vs 40%), 인용 수치는 원문 확인 후 사용한다.

### 2.3 문제 정의
> 강의실 노트북 시험에서 감독관은 학생 화면 안의 부정행위(다른 탭·앱 전환, 브라우저 내 AI 사용)를 볼 수 없고, 기존의 "N회 이탈 시 자동 종료" 방식은 놓치는 것도 많고 억울한 처벌도 만든다.

### 2.4 기술적 한계 (전제)
- **AI 사용 여부를 확정적으로 탐지하는 것은 불가능하다.** 이 서비스는 "AI를 썼다"고 판정하지 않고, 관찰된 행동(이탈, 사이드바 열림 의심 등)만 기록·표시한다.
- 웹 페이지는 휴대폰, 스마트워치, AI 안경 같은 **다른 기기**를 볼 수 없다. 이는 현장 감독과 시험 규정의 영역이다.
- 웹 페이지는 설치된 브라우저 확장 프로그램 목록을 볼 수 없다. 확장·사이드바 AI는 **흔적 기반 감지**만 가능하며, 일부는 실험으로 가능 여부를 확인해야 한다.

## 3. 해결 방법

### 3.1 핵심 아이디어
1. **알리고 → 사람이 확인하고 → 조치하고 → 기록한다.** 시스템은 판정하지 않는다.
2. **소수 감독관을 위한 실시간 좌석 대시보드.** 신호가 생긴 좌석이 즉시 표시된다.
3. **"기록되고 있다"는 인식을 억제 장치로 활용.** 사전 고지·동의와 응시 중 "기록 중" 표시.
4. **감지 기능의 효과를 정직하게 검증.** 우회 시나리오를 직접 시도해 무엇이 잡히고 무엇이 안 잡히는지 공개한다.

### 3.2 검토한 대안과 선택 이유
| 대안 | 판단 |
|---|---|
| 포커스 이탈 + N회 위반 자동 종료 (흔한 방식) | 오탐 시 억울한 처벌. → 자동 종료는 기본 꺼짐 옵션으로만 유지 |
| 전용 브라우저(Safe Exam Browser) 필수 | 같은 PC 안에서는 가장 강력하지만 개인 노트북 설치 부담·당일 장애 위험. → 고도화 과제 |
| 웹캠 감독·얼굴 인식 | 강의실에는 사람 감독관이 있어 효용이 낮고 개인정보 부담이 큼. → 제외 |
| AI 생성 글 판별기 | 오탐이 매우 높아 판정 근거로 부적합. → 제외 |
| 사후 검증(LLM 후속 질문), AI 내성 문항 점검, AI 허용·기록 모드 등 | 검토했으나 이번 프로젝트의 초점(행동 감지)과 다름. → 제외 |
| **웹 기반 + 행동 감지 + 감독관 실시간 확인** | 학생은 링크만 열면 되고, 강의실 감독관과 결합해 오탐 피해를 줄인다. → **선택** |

### 3.3 처음 생각에서 달라진 점 (요약)
- 코딩 시험 플랫폼 → **일반 시험(객관식+서술형) 플랫폼**. 코드 실행 샌드박스 부담을 덜고 무결성 기능에 집중. 코딩 문제는 고도화 과제.
- "3회 위반 시 종료" → **감독관 확인 후 조치**.
- 상세 이력은 `docs/DECISIONS.md`(예정)와 회고 문서에 기록.

## 4. 사용자와 사용 장면

### 4.1 사용자
| 사용자 | 목표 |
|---|---|
| 교수자 | 시험을 만들고, 시험을 시작·운영하고, 채점하고, 학생 체감 난이도를 다음 시험에 반영한다 |
| 조교 | 교수자와 함께 감독관으로서 대시보드를 보고 조치한다 |
| 학생 | 회원가입 없이 학번과 시험 비밀번호로 들어가 시험을 보고, 무엇이 기록되는지 알고 응시한다 |

### 4.2 대표 시나리오
1. 교수자가 시험(객관식+서술형), 수강생 명단, 무결성 설정을 등록하고 시험 URL을 공유한다.
2. 시험 당일, 교수자가 칠판에 시험 비밀번호(난수)를 적는다.
3. 학생은 URL에 접속해 **학번 + 난수**로 입장 → 본인 확인 → 사전 고지·동의 → 환경 점검(브라우저, 전체화면, 다중 모니터) → **대기실**에서 대기한다.
4. 교수자는 대시보드에서 입장 현황(예: 18/20명)을 확인하고 **[시험 시작]**을 누른다. 전원이 동시에 시작한다.
5. 응시 중 7번 좌석 학생이 다른 앱으로 전환한다 → 대시보드의 7번 좌석이 노란색으로 바뀌고 "앱 전환, 12초 이탈" 기록이 뜬다.
6. 조교가 7번 좌석으로 가서 확인하고, 필요하면 대시보드에서 경고 메시지를 보내거나 일시정지·종료한다. 조치와 사유가 기록된다.
7. 학생이 제출하면 **종료 설문**(체감 난이도 5점, 교수님께 하고 싶은 말)을 익명으로 남기고 퇴장한다.
8. 교수자는 객관식 자동 채점 결과를 확인하고 서술형을 채점한다. 학생별 신호 타임라인과 조치 기록을 검토하고, 설문 결과(난이도 분포, 점수 구간별 평균 체감 난이도, 의견)를 본다.

## 5. 기능 범위

### 5.1 1차 (필수)
| 영역 | 기능 |
|---|---|
| 시험 관리 | 교수자·조교 로그인, 시험 생성(객관식·서술형), 수강생 명단 등록, 시험 비밀번호(난수) 발급·재발급, 좌석 배치 설정, 무결성 설정 |
| 입장·대기 | 학번+난수 입장, 본인 확인, 중복 접속 차단, 사전 고지·동의, 환경 점검, 대기실, [시험 시작] 버튼, 지각생 승인 |
| 응시 | 학생별 문항·보기 순서 섞기, 문항 간 자유 이동, 답안 자동 저장, 재접속 이어 응시, 서버 기준 시간·자동 제출, "기록 중" 표시 |
| 행동 감지 | 탭 전환, 다른 앱 전환, 전체화면 해제, 연결 끊김, 이탈 시간, 붙여넣기(기록/차단) + 0단계 실험을 통과한 감지 항목 |
| 감독관 | 실시간 좌석 대시보드, 학생별 신호 타임라인, 경고 메시지·일시정지·재개·종료, 조치 기록 |
| 채점·결과 | 객관식 자동 채점, 서술형 수동 채점, 결과 공개 시점 설정 |
| 종료 설문 | 익명 체감 난이도·의견, 점수 구간별 집계 비교 |
| 배포·검증 | 외부 배포(HTTPS), 20명 동시 응시 부하 테스트, 평가용 데모 계정·데모 시험 |

### 5.2 0단계 실험 후 포함 여부 결정 (검증 필요)
화면 분할, 페이지 밖 마우스 이동, 두 번째 모니터, 단축키 시도, **AI 사이드바 열림(페이지 영역 축소)**, 전체화면 중 사이드바 동작, AI 확장 프로그램 흔적, 포커스 없는 상태의 입력(에이전트형 AI). 결과는 `docs/STUDY.md`.

### 5.3 2차 (우선순위 검토 후)
화면 공유 캡처(시험별 옵션), 서술형 작성 과정 기록·재생, 문제 풀(학생별 무작위 추출), 무결성 설정 프리셋, SEB 접속 '신뢰 높음' 표시, 자동 종료 옵션.

### 5.4 하지 않는 것
코딩 문제·자동 채점, 웹캠 감독, AI 글 판별기, 문항별 시간 제한, 실시간 화면 영상, SEB 필수화, 대규모(수백 명) 시험.

## 6. 성공 기준
| 기준 | 목표 |
|---|---|
| 외부 배포 | HTTPS 서비스 URL에서 시연 시나리오(4.2) 전 과정 동작 |
| 동시 응시 | 학생 20명 + 감독관 2명 부하 테스트에서 오류 없이 응시·제출 완료 |
| 실시간성 | 감지 신호 발생 후 대시보드 표시까지 2초 이내 |
| 답안 보존 | 네트워크 단절·새로고침 테스트에서 유실이 최대 5초 분량 이내 |
| 감지 검증 | 1차 감지 항목(탭·앱 전환, 전체화면 해제, 연결 끊김, 붙여넣기)이 Chrome·Edge의 우회 시나리오 테스트에서 재현 가능하게 기록됨. 안 잡히는 항목은 STUDY 문서에 한계로 명시 |
| 공정성 | 시스템 UI 어디에도 "부정행위/AI 사용" 판정 문구가 없음. 모든 조치에 실행자·시각·사유 기록 |

## 7. 운영 형태와 제약
- 목적: 기말 프로젝트 평가용 서비스. **성적에 반영되는 공식 시험 운영 계획 없음.**
- 검증 단계: 교수님 시연 → 가상 계정·테스트 데이터 기능 검증 → 20명 부하 테스트 → (가능하면) 자발적 참여자 소규모 시범 운영.
- 시범 운영 전 학교·교수님 측 별도 승인 필요 여부는 **미확인** → 확인 후 진행.
- 1인 개발, AI 코딩 도구 활용, 스펙 주도 개발(PRD → SPEC → 구현).
- 지원 브라우저: Chrome·Edge·Whale(Chromium 계열).
- 기술 구성: 프런트엔드 React(TypeScript) / 서버 Node.js + Socket.IO / DB PostgreSQL. 상시 구동 호스팅(월 5~10달러 수준).

## 8. 개인정보
- 수집: 학번·이름(명단), 행동 신호, 답안, 조치 기록, 익명 설문. (2차 기능 시 화면 캡처)
- 고지: 응시 전 수집 항목·보관 기간을 보여주고 동의를 받는다. 동의하지 않으면 응시 불가.
- 보관: 행동 신호·조치 기록 90일 후 자동 삭제. 화면 캡처는 시험별 설정(기본 30일).
- 설문: 교수자 화면에서 익명. 점수 구간 통계에만 사용하며, 응답이 5명 미만인 구간은 표시하지 않는다.

## 9. 위험 요소
| 위험 | 대응 |
|---|---|
