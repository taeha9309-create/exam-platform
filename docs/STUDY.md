## 1. 브라우저 이탈 감지 API

### 몰랐던 것
- 탭을 바꾸는 것(`visibilitychange`)과 창 포커스를 잃는 것(`blur`)이 **다른 이벤트**라는 점. 다른 앱으로 Alt+Tab 했을 때 어느 쪽이 발생하는지 모른다. (가설) 탭 전환은 둘 다, 다른 앱 전환은 `blur`만 발생한다.
- 전체화면(`requestFullscreen`)은 **사용자의 클릭이 있어야** 들어갈 수 있고 ESC로 언제든 풀린다. 그래서 "강제"가 아니라 "진입 요구 + 해제 감지"만 가능하다.
- 탭이 백그라운드에 있으면 브라우저가 타이머를 늦춘다. 이탈 시간을 타이머로 재면 부정확하므로 **떠난 시각과 돌아온 시각의 차이**로 계산해야 한다.
- 이벤트가 누락될 수 있어 `document.hasFocus()`를 1초마다 확인해 보완할지 모른다.

### 공부한 자료와 방법
- MDN: [Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API), [Window: blur event](https://developer.mozilla.org/en-US/docs/Web/API/Window/blur_event), [Fullscreen API](https://developer.mozilla.org/en-US/docs/Web/API/Fullscreen_API) (링크는 읽은 뒤 본인이 확인)
- 읽은 내용만으로 판단하지 않고, 모든 후보 이벤트를 시각과 함께 기록하는 **실험 페이지**를 만들어 직접 확인하는 방식으로 공부했다.

### 서비스에 적용한 과정과 결과
- 판정 로직(이탈·복귀 짝 맞추기, 지속 시간 계산)을 DOM과 분리한 순수 함수로 만들어 Node에서 단위 테스트했다(`experiments/detection-lab/detectors.js`).
- 이벤트가 뒤섞여 들어와도 시각순으로 처리하도록 만들었다.
- 실험 결과: (실험 후 기입)

## 2. 브라우저 안의 AI(사이드바·확장 프로그램) 흔적 감지 실험

### 몰랐던 것
- 웹 페이지는 **설치된 확장 프로그램 목록을 볼 수 없다**(브라우저 보안 정책). 그래서 "AI를 켰다"를 직접 알 수 없고, 켤 때 생기는 **흔적**만 잡을 수 있다.
- (가설) AI 사이드바가 열리면 브라우저 창(outer) 크기는 그대로인데 페이지 영역(inner)만 줄어든다. 창을 직접 줄이면 outer도 변하므로 구별할 수 있다.
- (가설) 일부 확장은 페이지에 요소를 끼워 넣어 `MutationObserver`로 잡힌다. 확장마다 달라서 일반적인 방법은 아닐 수 있다.
- (가설) 에이전트형 AI가 입력을 대신하면 "페이지에 포커스가 없는데 입력이 발생"하는 모순이 생긴다.
- 사이드바가 열린 것은 잡아도 **그것이 AI인지는 구분할 수 없다.** 화면 문구는 관찰 사실("사이드바 열림 의심")만 써야 한다.

### 공부한 자료와 방법
- MDN: [MutationObserver](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver), [Screen.isExtended](https://developer.mozilla.org/en-US/docs/Web/API/Screen/isExtended)
- 실험 페이지에서 시나리오별로 **Chrome·Edge 각 10회** 반복하고 JSON으로 저장 → 집계 스크립트로 표를 만들었다.

### 서비스에 적용한 과정과 결과
- **실험 환경(2026-11-29):** Windows 11, Google Chrome 158.0.8127.37, 모니터 1대(1920 너비), 사용한 AI: Chrome의 Gemini 사이드바, Chrome용 Claude 확장 사이드 패널. Edge는 설치돼 있으나(158.0.4370.x) **실험하지 못했다**(아래 한계).
- **실험 방식의 변경(사용자 승인):** SPEC 8장은 시나리오당 브라우저별 10회인데, 사람이 하는 400회는 현실적이지 않아 **시나리오당 5회로 줄였다.** 채택 기준 "10회 중 9회"는 "5회 중 5회"(100%)로 읽었다(4/5=80%는 기준 미달). 5회에서 5/5이어도 표본이 작아 "신호가 안정적으로 나온다"는 증거이지 확률 보증이 아니다.
- **자동화는 쓸 수 없었다:** Playwright로 탭 전환을 자동 실행해 봤더니 `visibilitychange`·`blur`가 한 건도 발생하지 않았다(Playwright가 모든 탭을 "포커스·표시 중"으로 에뮬레이트하기 때문). 자동 실험 결과는 전부 폐기하고 사람이 실제 브라우저에서 수행한 것만 집계했다. 같은 이유로 E2E 테스트(Task 10)는 이탈을 흉내 낸다(spec 주석 참고).
- **집계 결과**(`summarize.js` 출력, 칸은 "발생 회차/전체 회차"):

| 시나리오 | 회차 | VISIBILITY_HIDDEN | BLUR | SIDEBAR_SUSPECT | POINTER_LEAVE | DOM_INJECTED | 기타 |
|---|---|---|---|---|---|---|---|
| 다른 탭 이동 | 5 | 5/5 | 5/5 | 0 | 5/5 | 0 | |
| Alt+Tab | 5 | **4/5** | 5/5 | 0 | 5/5 | 0 | |
| 화면 분할 | 5 | 0/5 | 5/5 | 0 | 1/5 | 0 | |
| Chrome Gemini 사이드바 열기·사용 | 5 | 0/5 | 5/5 | **5/5**(−410px) | 5/5 | 0 | |
| Claude 확장 사이드 패널 열기·사용 | 5 | 0/5 | 5/5 | **3/5**(−386px) | 5/5 | 0 | |
| 사이드바 위에 커서만 올리고 읽기 | 5 | 0/5 | **0/5** | 0 | 4/5 | 0 | |
| 전체화면 중 사이드바 열기 시도 | 5 | 0 | 0 | 0 | 0 | 0 | 사이드바가 열리지 않음 |
| AI 확장이 페이지 읽기(패널 미리 열어 둠) | 5 | 0/5 | 5/5 | 0 | 5/5 | **1/5**(`<div>`) | |
| (오탐) 브라우저 권한 팝업 | **1** | 0 | 1/1 | 0 | 1/1 | 0 | 유효 회차 1회뿐 |

- **실험하지 못한 것(이유):** 두 번째 모니터 창 이동·커서 이동(모니터 1대), Edge Copilot 사이드바(사용 불가), Edge 전체(시간), 에이전트형 조작, 일상 행동 중 OS 알림·업데이트 창·덮개 절전·한/영 전환·한글 입력·터치패드(시간·환경). 권한 팝업은 "이번에만 허용"을 반복해 팝업을 다시 띄우기 어려워 첫 회차만 유효하다(2~4회차는 팝업이 안 떠 `results/_excluded/`로 제외).
- **발견한 사실:**
  1. **전체화면에서는 사이드바 자체가 보이지 않는다**(사용자가 직접 확인, 5회 모두 열리지 않음). 전체화면을 강제하면 사이드바 사용 자체가 막힌다 — 이 서비스가 전체화면 유지를 요구하는 설계(F-12)가 사이드바 우회에도 유효하다는 근거.
  2. **AI 패널을 "사용"하면 `BLUR`가 5/5로 나온다**(패널에 타이핑하려면 포커스가 패널로 옮겨가므로). 즉 이미 구현된 `LEAVE`(창 포커스 상실)가 패널 사용을 잡는다. 반면 **커서만 올려 읽기만 하면 `BLUR`가 0/5**라 못 잡고 `POINTER_LEAVE`만 4/5로 나온다.
  3. **사이드바가 열리는 순간**은 `SIDEBAR_SUSPECT`(페이지 너비만 줄고 창 바깥 너비는 그대로)로 잡힌다. Gemini는 5/5, Claude 확장은 3/5 — 2·3회차에는 크기 변화가 기록되지 않았다(패널이 이미 열려 있던 것으로 추정, 미확인). **이미 열려 있는 사이드바는 이 방법으로 알 수 없다.**
  4. 화면 분할은 `VISIBILITY_HIDDEN`이 0이고 `BLUR`만 나온다(창이 가려지지 않으므로). Alt+Tab도 다른 창이 Chrome을 완전히 가리지 않으면 `HIDDEN`이 안 나온다(4/5). 그래서 **이탈 판정은 `visibilitychange`만이 아니라 `blur`도 함께 써야 한다**(SPEC 5.1 `LEAVE`가 이미 그렇게 정의됨, 맞는 설계였다).
  5. AI 확장이 페이지에 요소를 끼워 넣는 일은 5회 중 1회(`DOM_INJECTED`)였다 — 일반적인 방법이 아니다.
- **채택/제외 판단과 근거(제안, 사용자 승인 대기):**
  - `LEAVE`(`blur`+`hidden`): **이미 SPEC에 있음. 유지.** 탭 전환·Alt+Tab·화면 분할·AI 패널 사용을 5/5로 잡는다. 단 일상 행동 오탐은 1회(권한 팝업)만 측정해 `BLUR`가 팝업에도 발생함을 확인했다 → 그래서 위반 카운트는 3초 이상 이탈만 센다(구현됨).
  - **`SIDEBAR_SUSPECT`: 조건부 채택 제안.** Gemini 5/5이지만 Claude 확장 3/5로 엄격 기준(전부)에는 미달이다. 대신 "사이드바 열림 의심"이라는 관찰 사실을 **`INFO` 등급(위반 카운트·자동 잠금에 넣지 않음)** 으로 기록하면 감독관에게 참고 정보가 되고, 오탐(창 크기를 직접 줄임은 바깥 너비도 변하므로 구분됨) 위험이 낮다. 일상 행동 오탐은 충분히 측정하지 못했다(한계).
  - `POINTER_LEAVE`: **제외 제안.** 사이드바 읽기만 하는 경우 4/5(기준 미달), 일상 행동(권한 팝업)에서도 발생(1/1), 터치패드·전체화면 상단 오탐은 측정하지 못했다. 위반 카운트에 넣으면 오탐으로 학생을 잠글 위험이 크다.
  - `DOM_INJECTED`: 1/5 → 제외.
  - `MULTI_MONITOR`·`INPUT_WITHOUT_FOCUS`·`LARGE_SELECTION`: 이번 환경에서 대상 시나리오를 수행하지 못해(또는 우연 1회) 판단하지 않는다(MULTI_MONITOR는 이미 SPEC에 서버 신호로 있음).
- 채택된 항목은 SPEC 5.1에 신호 행으로 추가(버전 올림)하고 결정 기록에 남긴다 → 계획 2 Task 11(사용자 승인 후).

## 3. 커서가 페이지 밖으로 나가면 화면 가림 (SPEC 5.6)

### 몰랐던 것
- 전체화면 + 모니터 1대에서는 커서가 원래 페이지 밖으로 나갈 수 없다. (가설) 그래서 이 신호는 주로 **두 번째 모니터로 이동**하거나 **AI 사이드바 위에 커서를 올린 경우**를 잡는다.
- 브라우저 기본 팝업(`<select>` 등)이 열릴 때 `mouseleave`가 발생하는지 모른다.

### 공부한 자료와 방법
- 실험 페이지에 "커서 이탈 시 화면 가림" 옵션과 브라우저 기본 `<select>`를 넣어 직접 확인한다.

### 서비스에 적용한 과정과 결과
- 1초 미만은 기록하지 않고, 1~3초 정보 / 3~15초 주의 / 15초 초과 경고로 나누는 판정 함수를 구현·테스트했다.
- 결과(Chrome 158, 모니터 1대, 시나리오당 5회): 사이드바 위에 커서만 올리고 읽기만 하는 경우 `POINTER_LEAVE`가 **4/5**(1회는 머문 시간이 1초 미만으로 보여 신호 없음)이고 `BLUR`는 0/5라 이 행동은 `POINTER_LEAVE`만이 단서다. 그러나 일상 행동인 **브라우저 권한 팝업에서도 `POINTER_LEAVE`가 발생**했다(1/1, 팝업이 뜨면 커서가 페이지 밖으로 판정됨). 터치패드·전체화면 상단 오탐은 측정하지 못했다. → **기준(5/5)에 미달이고 오탐이 확인되어 위반 카운트에는 넣지 않는 것을 제안**한다(STUDY 2절 판단 참고, 사용자 승인 대기). 5.6의 "커서가 나가면 화면 가림"은 학생 화면을 불필요하게 가려 오탐 시 학생에게 불리하므로 채택하지 않는 쪽이 안전하다.

| 행동 | 브라우저 | POINTER_LEAVE | 판단 |
|---|---|---|---|
| 커서를 두 번째 모니터로 이동 | Chrome / Edge | **미실험**(모니터 1대) | |
| 커서를 AI 사이드바 위에 올리고 읽기만 | Chrome | **4/5** | 기준 미달(5/5 필요). BLUR 0/5라 이 신호가 유일한 단서 |
| 터치패드로 입력 중 커서가 가장자리로 밀림(오탐) | Chrome / Edge | **미실험** | |
| 전체화면에서 커서를 화면 상단에 댐(오탐) | Chrome / Edge | **미실험** | |
| 브라우저 권한 팝업(오탐) | Chrome | **1/1** | 일상 행동에서 발생 → 오탐 |

## 4. 일상 행동에서의 오탐 측정

### 몰랐던 것
- 정직한 학생도 포커스를 잃는 일상적인 상황이 많다(권한 창, OS 알림, 업데이트 창, 노트북 덮개·절전, 한/영 전환, 한글 조합 입력). 어느 신호가 이런 상황에서 발생하는지 모른다.

### 공부한 자료와 방법
- 대상 행동 실험과 같은 페이지에서 일상 행동 시나리오 8종을 각 10회 수행한다.

### 서비스에 적용한 과정과 결과
- 규칙: 같은 신호가 일상 행동에서 **10회 중 2회 이상** 발생하면 해당 신호는 위반 횟수에 넣지 않는다(위반 카운트는 5회마다 자동 잠금과 연결되므로 오탐이 특히 중요하다).
- **결과(한계가 큼):** 일상 행동 8종 중 **브라우저 권한 팝업 1종만 1회 유효하게 측정**했다(시간·환경 문제로 나머지는 미실험, 위 2절 참고). 그 1회에서 `BLUR`와 `POINTER_LEAVE`가 모두 발생했다 — 즉 **일상적인 팝업에도 "창 포커스 상실"이 일어난다.** n=1이라 비율은 말할 수 없지만 "이 신호들이 오탐을 낼 수 있다"는 존재 증명은 된다.
- **서비스에 적용한 결과:** (1) 이 결과가 이미 구현한 **"3초 미만의 이탈은 기록만 하고 위반으로 세지 않는다"**(SPEC 5.7, `LEAVE_VIOLATION_MS`)와 **"위반은 감독관이 확인 후 조치하고 시스템은 판정하지 않는다"** 설계를 뒷받침한다 — 짧은 팝업·알림은 위반에서 빠지고, 길게 이탈한 경우도 감독관이 확인한다. (2) `POINTER_LEAVE`를 위반 카운트에 넣지 않는 제안의 근거가 된다. (3) **측정하지 못한 오탐(한/영 전환, 한글 입력, 터치패드, 전체화면 상단, OS 알림, 절전 복귀)은 한계로 남긴다.** 이들은 주로 `blur`·`mouseleave`와 관련되는데, 현재 위반 카운트 대상은 `LEAVE`(≥3초)·`FULLSCREEN_EXIT`·`PASTE`·`DROP`뿐이라 한글 입력·한/영 전환이 직접 위반을 만들 가능성은 낮지만 **실측으로 확인하지 않았다.** 시범 운영(자발적 참여자)에서 오탐 보고를 받는 것으로 보완한다.

## 5. 구현 전에 실험 페이지부터 검증한 방법 (헤드리스 브라우저)

### 몰랐던 것
- 실험 페이지 자체에 버그가 있으면 실험 결과를 믿을 수 없다. 사람이 하는 실험 전에 페이지가 "이벤트를 받으면 올바르게 기록하는지"를 먼저 확인해야 한다.

### 공부한 자료와 방법
- Chrome DevTools Protocol(CDP): 헤드리스 Chrome을 원격 디버깅 포트로 띄우고, WebSocket으로 접속해 페이지에서 코드를 실행한다.

### 서비스에 적용한 과정과 결과
- 일회용 스크립트로 헤드리스 Chrome 158을 구동해 이벤트(탭 숨김, blur, 창 크기 변화, 커서 이탈, DOM 삽입, 포커스 없는 입력, 선택)를 코드로 발생시켰다.
- 결과: 후보 신호 7종이 기록되고, 이 페이지가 만든 요소는 `DOM_INJECTED`에서 제외되며, 기록 정지 중에는 이벤트가 쌓이지 않고, 페이지 오류는 0건이었다.
- **한계:** 이벤트를 코드로 발생시킨 것이라 "받으면 기록한다"까지만 증명한다. 실제 브라우저가 어떤 이벤트를 주는지는 사용자의 실험으로만 알 수 있다(전체화면 해제, 두 번째 모니터 등은 이 방법으로 검증하지 못했다).

## 7. 배포: 프록시 뒤에서 달라지는 것들

이 절은 **배포 전에** 코드·ADR·테스트에서 확인되는 사실만 적은 것이다. 실제 배포 결과와 수치는 아직 없으며, 확인하지 못한 것은 "미확인"으로 표시했다. 배포 플랫폼은 처음 Railway로 조사했다가 **Render 무료 요금제**로 바뀌었다(사용자 결정). 플랫폼 사실은 웹 검색으로 확인한 Render 공식 문서 기준 내용이며 배포 시점에 화면·문서로 다시 확인해야 한다.

### 몰랐던 것
- **프록시 뒤의 `req.ip`**: 프록시가 있으면 서버가 보는 연결 상대는 프록시라서, 기본값으로는 모든 요청의 IP가 같게 보인다. 그래서 `X-Forwarded-For` 헤더를 읽어야 하는데, 이 헤더는 클라이언트가 직접 써서 보낼 수도 있다. Express의 `trust proxy`에 **프록시가 몇 겹인지(홉 수)** 를 정확히 알려 줘야 한다. 프록시가 없는데 켜면 IP를 위조당하고(로그인 시도 제한 우회), 실제보다 적게 잡으면 모두 프록시 IP로 보여 전원이 함께 차단된다. 이 서버는 `NODE_ENV=production`일 때만 `trust proxy`를 켜고 기본값은 1이며, 환경변수 `TRUST_PROXY_HOPS`(1~3의 정수만, 그 밖의 값은 서버가 시작을 거부)로 조정할 수 있다(`server/src/config.ts`의 `parseTrustProxyHops`, `server/src/index.ts`). Render 프록시가 실제로 몇 겹인지는 공식 문서에서 **확인하지 못했다(미확인)**. 커뮤니티 보고로는 Render 프록시가 클라이언트가 보낸 `X-Forwarded-For`를 지우지 않고 뒤에 덧붙인다고 하므로, 홉 수가 맞아야 위조 값이 아니라 프록시가 덧붙인 값이 쓰인다. 그래서 배포 후 위조 헤더로 한도 우회 여부를 직접 시험하도록 했고, 홉 수를 코드 변경 없이 환경변수 `TRUST_PROXY_HOPS`로 조정할 수 있게 했다. 이 값은 보안 설정이라 `0`·`true`·이름·공백이 섞인 값은 받지 않고(정규식 `/^[1-3]$/`, 전각 숫자와 끝 개행도 거부됨을 Opus 리뷰에서 확인) 시작 자체를 거부한다.
- **Origin 검사와 `Host`·`X-Forwarded-Proto`**: 같은 출처인지 `스킴://Host`를 만들어 Origin과 문자열 전체로 비교한다(`originCheck.ts`). 프록시가 TLS를 끝내면 서버는 `http`로 받으므로 스킴을 `X-Forwarded-Proto`에서 가져와야 `https` Origin과 맞는다. HTTP API는 `trust proxy`가 켜진 경우 `req.protocol`이 이를 따른다. 웹소켓 쪽은 `socket.ts`가 직접 헤더를 읽는데, **production에서만** 이 헤더를 믿는다(헤더는 위조 가능하므로 프록시가 없는 개발·테스트에서는 무시, `trust proxy`와 같은 조건).
- **웹소켓의 Origin 검사와 JSONP 폴링 우회**: 웹소켓 핸드셰이크와 fetch 폴링은 브라우저가 Origin을 붙이지만, Engine.IO의 JSONP 폴링은 `<script src>`로 요청되어 **Origin 없이 쿠키가 실릴 수 있다**. Origin이 없으면 허용하는 규칙만으로는 이 경로가 통과한다. 코드 리뷰(작업 지시서 기준 Opus 리뷰)에서 발견되어, `allowRequest`에서 JSONP(`j` 쿼리)를 거부하고 Origin이 없을 때는 `Sec-Fetch-Site`가 `same-origin`·`none`이 아니면 거부하도록 수정했다. 테스트: `server/test/realtime.test.ts`("JSONP·Fetch Metadata·옵션").
- **Secure 쿠키와 HTTPS**: 교수자 쿠키는 `httpOnly`, `sameSite: 'lax'`이고 `secure`는 production에서만 켠다(`staffAuth.ts`). Secure 쿠키는 HTTPS에서만 전송되므로 production을 `http`로 열면 로그인 쿠키가 붙지 않는다(개발은 `http://localhost`라 꺼 둔다).
- **설정 파일 대신 서비스 설정**: ADR-012는 Railway의 `railway.json`이 폐지(2026-12-01 이후 읽지 않음)되어 설정 파일을 쓰지 않기로 한 결정이다. 플랫폼이 Render로 바뀐 뒤에도 `render.yaml` 같은 설정 파일 없이 대시보드 설정(Build·Start 명령)과 표준 `package.json` 스크립트를 쓴다. 결과적으로 방식은 같지만 ADR-012의 내용(Railway, Pre-deploy)과는 어긋나므로 **ADR 갱신은 별도 사용자 승인이 필요하다**(이 문서에서는 고치지 않았다). 대가로 설정이 코드로 버전 관리되지 않아 README 절차에 의존한다.
- **무료 플랫폼의 제약(Render 공식 문서 기준)**: (1) 무료 웹 서비스는 15분간 인바운드 트래픽(기존 웹소켓 메시지 포함)이 없으면 잠들고 다음 요청·새 웹소켓 연결 때 약 1분에 걸쳐 깨어난다. (2) 무료 Postgres는 만든 지 30일 뒤 만료(14일 유예 후 삭제), 1GB, 백업 없음. (3) **무료 인스턴스에서는 Pre-deploy Command를 쓸 수 없다**(유료 전용). (4) 파일시스템이 휘발성이고 커스텀 도메인이 없다.
- **Pre-deploy를 못 쓸 때의 마이그레이션**: ADR-012는 마이그레이션을 Pre-deploy에 두면 새 버전이 뜨기 전에 실행되고 실패 시 배포가 중단된다고 했다. 무료에서는 불가하므로 Start Command 앞에 붙인다(`npm run db:deploy -w @exam/server && npm start`). 적용할 마이그레이션이 없으면 바로 끝나 깨어날 때마다 돌아도 안전하고, `&&` 때문에 실패하면 서비스가 시작되지 않는다. 다만 Pre-deploy와 달리 실패해도 이전 버전이 계속 떠 있는지(롤아웃 중단)는 **미확인**이다.
- **`PORT`와 바인딩**: Render는 `PORT`(기본 10000)를 주입하고 0.0.0.0 바인딩을 요구한다. 서버는 `PORT`를 읽고 `httpServer.listen(port)`에 호스트를 지정하지 않아(Node 기본값, 모든 인터페이스) 코드상 맞는 것으로 확인했다. 실제 동작은 배포 후 확인한다.

### 공부한 자료와 방법
- 읽은 코드: `server/src/app.ts`, `index.ts`, `static.ts`, `security/originCheck.ts`, `realtime/socket.ts`, `auth/staffAuth.ts`, `scripts/demo-reset.ts`. 읽은 문서: `docs/DECISIONS.md`의 ADR-012(및 ADR-003·004·005의 관련 부분).
- 테스트로 확인된 것: 화면 폴백·404 규칙(`static.test.ts`), Origin 검사 규칙(`originCheck.test.ts`), 소켓 JSONP·Fetch Metadata(`realtime.test.ts`).
- 플랫폼 제약(잠듦·DB 30일 만료·Pre-deploy 불가·PORT)은 웹 검색으로 찾은 Render 공식 문서 내용을 전달받아 반영했다(이 절 작성자가 원문을 직접 열어 보지는 않았다). 프록시 홉 수와 `X-Forwarded-For` 처리는 공식 문서에서 찾지 못했고 커뮤니티 보고만 있다(**미확인**). Express `trust proxy` 문서도 새로 읽지 않았다. 배포 후 실제 헤더를 확인해야 한다.
- 미확인: 무료 요금제의 카드 등록 필요 여부, 무료 DB의 외부(External) 접속 허용·IP 허용 목록 기본값, 서비스 중지·삭제 메뉴 이름, `.node-version` 24 지원 여부(빌드 로그에서 확인).

### 서비스에 적용한 과정과 결과
- 운영에서만 `trust proxy`(1)를 켜고, 로그인·입장 시도 제한은 `req.ip`만 쓴다(헤더를 직접 파싱하지 않음). 위조 가능성은 홉 수가 맞아야 막힌다는 전제에 의존한다.
- HTTP와 웹소켓 모두 Origin을 문자열 전체 일치로 검사하고, 소켓에는 JSONP 차단과 Fetch Metadata 검사를 추가했다. 단, 소켓의 Origin 규칙은 `originCheck.ts`와 **복제**되어 있어 규칙을 바꾸면 두 곳을 함께 고쳐야 한다(`socket.ts` 주석).
- 데모 데이터는 서비스가 아니라 사용자 PC에서 `demo:reset`으로 만든다. `DEMO_STAFF_PASSWORD`·`DEMO_PASSCODE`는 서버 코드가 읽지 않으므로 서비스 변수에 두지 않는다(README "배포 (Render 무료)").
- 무료 제약을 설계에 반영했다: 마이그레이션을 Start Command 앞으로 이동, DB는 제출·평가 시점(12/7 전후)에 맞춰 만들고 만료 전에 새 DB를 만들어 `demo:reset`으로 다시 채우는 절차, 시연 몇 분 전 서비스 깨우기와 평가자 안내 문구("처음 접속이 느리면 1분 기다리세요"). 외부 핑으로 깨워 두는 방식은 효과·약관을 확인하지 못해(미확인) 권하지 않는다.

## 8. 부하·실시간성·답안 보존 측정 (계획 3, SPEC 9장 성공 기준 2·3·4)

### 몰랐던 것
- "20명이 동시에 응시해도 되는가"를 사람 20명 없이 재현하는 방법: 실제 클라이언트와 같은 프로토콜(`socket.io-client`)로 가상 학생을 만들면 서버·DB·소켓 경로를 그대로 지난다. 다만 서버와 클라이언트가 같은 PC면 네트워크 지연이 사실상 0이라 **상한(가장 좋은 경우) 측정**일 뿐이다.
- 실시간성은 "서버가 받은 시각"이 아니라 **학생이 보낸 시각부터 교수자 화면이 받은 시각까지**로 재야 사용자가 느끼는 지연에 가깝다(같은 프로세스 시계 하나로 재서 시계 오차 없음).
- 테스트가 "통과했다"와 "검증했다"는 다르다: 빈 목록에 `every()`를 쓰면 참이 되고, 오프라인 차단이 안 먹어도 "서버에 없다"는 단정은 통과할 수 있다. 리뷰에서 이런 **거짓 통과 경로**를 찾아 막았다.

### 공부한 자료와 방법
- SPEC 9장의 합격 기준을 그대로 수치화: 제출 20/20, 서버 5xx 0, 교수자 소켓 수신 누락 0, 신호 지연 95% ≤ 2초.
- Playwright 오프라인 에뮬레이션(`context.setOffline`)을 직접 확인: 기존 WebSocket을 닫지 않고 **전송만 막는다**. 그래서 소켓 `close` 이벤트가 아니라 WebSocket 프레임(전송 시도)과 ack 수신 수로 차단을 확인했다.
- 변이 시험(일부러 틀리게 고쳐 테스트가 잡는지 확인)으로 안전장치(운영 서버 보호용 호스트 검사 등)가 테스트로 고정되어 있는지 점검.

### 서비스에 적용한 과정과 결과
**부하·실시간성** (`npm run load-test`, 결과 `docs/load-test-results/2026-11-28-local-20students.json`)
- 환경: Windows 11, Node v24.20.0, Intel i7-12700F(20스레드)·32GB, PostgreSQL 16(로컬 docker), 서버·가상 학생·교수자 소켓이 같은 PC의 localhost(운영 서버 아님), 측정일 2026-11-28.
- 시나리오: 가상 학생 20명 입장 → 동의·환경 점검 → 대기 → 시작 → 90초간 하트비트(5초)·`answer:save`(약 10초)·`signal`(약 12초) → 제출. 4명은 도중에 소켓을 3~12초 끊었다 재연결. 교수자 소켓 2개가 `signal:new` 수신. 신호 주기는 90초 안에 표본 100건 이상을 얻으려고 SPEC의 2분보다 압축했다.
- 결과: 제출 **20/20**, 답안 보존 **20/20**(제출 직전 서버 저장분 = 마지막 ack), 서버 5xx **0**, 교수자 소켓별 수신 누락 **0/0**, `answer:save` 188회 실패 0. 신호 150건(소켓별 수신으로 지연 표본 300개) **p50 13.1ms, p95 23ms, 최대 43.7ms**(기준 p95 ≤ 2000ms). 합격.
- 한계: 로컬 상한 측정이다. 교실 와이파이·Render 무료 서버의 값은 이보다 클 수 있어 별도 수동 확인이 필요하다. 20명보다 큰 규모, 실제로 느린 교수자 소켓(전송 계층 지연)은 측정하지 않았다.

**답안 보존** (`e2e/answer-preservation.spec.ts`, 로컬 전용)
- 서술형 입력 → 네트워크 차단 → 추가 입력 → 새로고침 → 복구 → 화면과 서버 모두에 답이 남는지. 차단이 실제로 작동했는지(`navigator.onLine`, 전송 시도 관찰, ack 불변)를 먼저 단정해 거짓 통과를 막았다. 시나리오 3회 반복 통과, 전체 E2E 6/6 통과. 수동 10회(PRD 기준 4)는 사용자 몫으로 남았다.

**공정성** (금지어 정적 검사)
- 금지어 검사를 `ko.ts`에서 `client/src` 전체 화면 소스로 확대. 같은 줄 블록 주석 뒤 코드·JSX 텍스트의 금지어까지 잡도록 보강했고(리뷰 지적), 현재 화면 문구의 금지어는 0건이다. 조치 기록 통합 테스트는 `server/test/actions.test.ts`에 있다.
