# 하네스 안전장치 검증 절차와 남은 위험

하네스 설정(ADR-010, ADR-011, D-023, `CLAUDE.md`)이 **실제로 동작하는지** 수동 사이클에서 확인한다. 결과는 `docs/STUDY.md`의 "하네스 엔지니어링" 절 근거로 쓴다.

> **핵심 원칙 (2026-11-25 수동 검증에서 얻음):** 권한 모드에 따라 동작이 바뀌는 장치는 안전장치로 믿지 않는다. `deny`(모든 모드에서 차단)와 서버 강제(GitHub)만 강제 장치로 보고, `ask`(승인 요청)는 기본 모드에서만 의미 있는 보조 장치로 본다.

## 1. 방어 계층

| 계층 | 장치 | 강제력 | 막는 것 | 우회 가능성 |
|---|---|---|---|---|
| L1 Claude Code 권한 | `.claude/settings.json` | `deny`: 강제 / `ask`: **auto 모드에서는 사람에게 묻지 않음** | `deny`: `.env`·키 파일 읽기, 강제 push, `gh pr merge` / `ask`: 편집 도구로 보호 문서 변경 | auto 모드에서 보호 문서 로컬 수정은 막히지 않음 → L3 |
| L2 셸 훅 | `.claude/hooks/guard-shell.mjs` (Bash·PowerShell) | `deny`: 강제 / `ask`: L1과 같음 | `deny`: **모든 경로의 PR 병합**(`pr merge`, 자동 병합, REST `pulls/N/merge`, GraphQL 병합·자동 병합), 승인 라벨 부착(이름·GraphQL), `.env` 접근, main·강제 push, `--no-verify`, 보호 설정·설정 스크립트 / `ask`: 보호 경로 + 쓰기 흔적 | 경로를 문자열로 드러내지 않는 스크립트, 문자열 조합·인코딩, 스크립트 내부에서 API 호출 → L3·L4·L5 |
| L3 GitHub CI | `protected-files`, `review-gate`, `test` 필수 검사 | 서버 강제 | 보호 파일 변경 PR은 승인 라벨 없으면 실패, `중요-리뷰` PR은 현재 커밋의 Reviewer 승인 댓글 없으면 실패 | PR에서 워크플로 파일을 고치면 검사 자체를 바꿀 수 있음, 승인 댓글 위조 → L5 |
| L4 브랜치 보호 | ruleset `protect-main` (우회 대상 없음, 필수 검사는 Actions 앱 15368만 인정) | 서버 강제 | main 직접·강제 push, 삭제, 필수 검사 실패 상태의 병합, 가짜 성공 상태 | 저장소 소유자가 웹에서 규칙을 끄는 것 |
| L5 사람 | **병합은 사용자만**(D-023), 승인 라벨은 사용자만 | 사람 | 모든 병합과 보호 문서 변경의 최종 확인 | 사용자가 diff를 보지 않고 병합하는 것 |

## 2. 비밀값 원칙
- `.env`는 로컬 개발용 값만 둔다. 운영 비밀값은 Railway·GitHub Secrets에만, 사용자가 직접 입력.
- 앱(서버·테스트)은 실행 시 `.env`를 읽는다. 막을 수 없고 막으면 안 된다. L1·L2의 `.env` 차단은 **에이전트가 내용을 대화에 출력·유출하는 것**을 막는 장치다.
- `.gitignore`가 `.env`, `.env.*`(예시 제외), `*.pem`, `*.key`를 제외. 공개 전 전체 이력 검사 완료(2026-11-25: 비밀값·개인정보 0건, 커밋 이메일은 noreply로 재작성).

## 5. 승인 장치 자체를 우회하는 경로

| 경로 | 어떻게 우회되나 | 현재 대응 | 남는 위험 |
|---|---|---|---|
| 병합 명령 | 전체 경로(`"…/gh.exe" pr merge`), 변수(`"$GH" pr merge`), 자동 병합(`--auto`), REST(`pulls/N/merge`), GraphQL(`mergePullRequest`) | 훅이 실행 파일 이름이 아니라 **동작**으로 판단해 모두 거부, 설정 `deny`도 추가 | 문자열을 쪼개거나 인코딩해 스크립트 안에서 API 호출 → 탐지 불가. 단, 병합되어도 L3·L4는 통과해야 하고 PR 타임라인에 "누가 병합했는지"가 남음 |
| `문서변경-승인` 라벨 | 에이전트가 라벨을 붙이면 `protected-files` 통과 | 라벨 이름이 든 명령 거부, GraphQL 라벨 부착(`addLabelsToLabelable`, 라벨 ID 사용) 거부 | REST로 라벨 ID·이름을 조합하거나 인코딩하면 탐지 불가. GitHub는 같은 토큰이라 구분 못 함 → **병합 전에 사용자가 이슈 타임라인에서 라벨을 누가 붙였는지 확인** |
| Reviewer 승인 댓글 | Coordinator가 `harness-review: APPROVED sha=…` 댓글을 직접 씀 | 커밋 SHA에 묶임 | 위조 방지 불가 → 사용자가 병합 전 Reviewer 판정 내용과 대조 |
| CI 설정 파일 변경 | `pull_request` 이벤트는 PR 쪽 워크플로로 실행 → PR에서 검사를 "항상 통과"로 바꿀 수 있음(작업 이름 유지) | 워크플로 변경은 L1·L2 보호 대상, `protected-files` 감지(단, 고친 워크플로로 돌면 무력화 가능) | **워크플로를 바꾸는 PR은 사용자가 diff를 직접 읽고 병합**. 강한 대안(`pull_request_target`, CODEOWNERS + 2인 리뷰)은 1인·2주 규모에 과해 미적용 |
| 하네스 설정 파일 | `.claude/settings.json`·훅·CLAUDE.md를 고쳐 장치를 끔 | `protected-files`가 감지 → 사용자 라벨 필요 | 로컬 세션에서는 수정 즉시 효과가 날 수 있음(병합 전이라도) → 사용자가 PR 외 로컬 변경도 `git status`로 확인 |
| 가짜 성공 상태 | 커밋 상태 API로 같은 이름의 성공을 올림 | 필수 검사를 Actions 앱(15368) 결과로만 인정 | 없음(서버 강제) |
| 초기 push | `gh repo create --push` | 저장소 생성 1회 | 이후 ruleset이 서버에서 막음 |

**결론:** 이 하네스는 **"실수와 무심한 우회"를 막고, 의도적 우회는 흔적이 남게 하는** 장치다. 같은 계정·같은 토큰을 쓰는 1인 구조에서 의도적 우회를 완전히 막을 수는 없다. 그래서 **병합을 사람만 하도록 하고(D-023)**, 병합 전에 사람이 확인할 것을 정해 둔다.

**사용자 병합 전 확인 목록**
1. CI 필수 검사 3개 모두 초록
2. 보호 파일(문서·`.claude/**`·워크플로) 변경이 있으면 diff를 직접 읽었는가
3. `중요-리뷰` PR이면 Reviewer 판정 댓글이 실제 Reviewer 결과(Coordinator 보고)와 일치하는가
4. 승인 라벨을 내가 붙였는가(이슈 타임라인)

## 7. 현재 하네스의 한계 (발표·회고용)
1. **auto 모드에서는 로컬 `ask`가 무력하다.** 보호 문서의 로컬 수정은 막히지 않고, PR 단계(L3)와 사람(L5)에서 잡힌다.
2. 셸 훅은 명령 문자열만 본다: 경로를 숨긴 스크립트, 문자열 조합·인코딩, 스크립트 내부 API 호출은 탐지 불가. 반대로 이름이 들어 있기만 해도 막는 오탐이 있다(5건 기록).
3. 같은 GitHub 계정·토큰을 쓰므로 라벨 부착·리뷰 댓글의 "누가"를 GitHub가 구분하지 못한다 → 사람 확인.
4. PR에서 워크플로 파일을 고치면 CI 검사 자체를 바꿀 수 있다 → 워크플로 변경 PR은 사람이 diff 확인.
5. 대화형 세션에는 강제 비용 한도가 없다(헤드리스만 가능).
6. 1인 저장소에서는 "승인 리뷰 N개 필수"를 쓸 수 없다(작성자는 자기 PR 승인 불가) → 필수 상태 검사로 대체.
7. 2026-11-25 Coordinator가 Python 스크립트로 SPEC을 수정한 사례(승인된 변경이었으나 L1을 거치지 않음) — L2·L3을 만든 계기.
