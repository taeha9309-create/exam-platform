# 하네스 안전장치 검증 절차와 남은 위험

하네스 설정(ADR-010, ADR-011, `CLAUDE.md`)이 **실제로 동작하는지** 수동 사이클에서 확인한다. 결과 칸을 채워 `docs/STUDY.md`의 "하네스 엔지니어링" 절 근거로 쓴다.

## 1. 방어 계층

| 계층 | 장치 | 막는 것 | 우회 가능성 |
|---|---|---|---|
| L1 Claude Code 권한 | `.claude/settings.json` `ask`/`deny` | 편집 도구(Edit·Write 등)로 보호 문서 변경 → 승인 창, `.env`·키 파일 읽기 차단 | 셸 명령은 대부분 해당 없음 → L2 |
| L2 셸 훅 | `.claude/hooks/guard-shell.mjs` (Bash·PowerShell) | 명령 문자열에 보호 경로 + 쓰기 흔적 → 승인 창, `.env` 접근·강제 push·main push·`--admin`·보호 설정·`--no-verify`·`문서변경-승인` → 거부, `gh pr merge` → 승인 창 | **경로를 문자열로 드러내지 않는 스크립트**(인자로 받은 폴더 안 파일 수정 등), 셸 변수로 조합한 경로 → L3·L4 |
| L3 GitHub CI | `protected-files`, `review-gate`, `test` 필수 검사 | 보호 문서 변경 PR은 `문서변경-승인` 라벨 없으면 실패, critical PR은 현재 커밋의 Reviewer 승인 댓글 없으면 실패 | 승인 댓글은 같은 계정이 쓸 수 있음(위조 방지 아님) → L4 |
| L4 브랜치 보호 | ruleset `protect-main` (우회 대상 없음) | main 직접 push, 강제 push, 삭제, 필수 검사 실패 상태의 병합 | 저장소 소유자가 웹에서 규칙을 끄는 것(사람의 행동) |
| L5 사람 | `gh pr merge` 승인 창, `문서변경-승인` 라벨은 사용자만 | 모든 병합과 보호 문서 변경의 최종 확인 | 사용자가 내용을 보지 않고 승인하는 것 |

**결론:** 로컬(L1·L2)에서 완전 차단은 불가능하다. 특히 임의 스크립트를 통한 간접 수정은 원리적으로 잡을 수 없다. 그래서 **변경이 main에 들어가는 지점(L3·L4·L5)을 강제 관문**으로 둔다.

## 2. 비밀값 원칙
- `.env`는 로컬 개발용 값만 둔다(로컬 Docker DB 비밀번호, 개발용 JWT 비밀값). 운영 비밀값은 Railway·GitHub Secrets에만, 사용자가 직접 입력.
- 앱 자체(서버·테스트)는 실행될 때 `.env`를 읽는다. 이것은 막을 수 없고 막으면 안 된다. 따라서 L1·L2의 `.env` 차단은 **에이전트가 내용을 대화에 출력·유출하는 것**을 막는 장치다.
- `.gitignore`가 `.env`, `.env.*`(예시 파일 제외), `*.pem`, `*.key`를 제외한다. 공개 전에 Git 이력 전체를 검사한다(2026-11-25 1차 검사: 비밀값 없음, 커밋 이메일만 개인 주소).

## 5. 승인 장치 자체를 우회하는 경로 (2026-11-25 분석)

| 경로 | 어떻게 우회되나 | 현재 대응 | 남는 위험 |
|---|---|---|---|
| `문서변경-승인` 라벨 | 에이전트가 라벨을 붙이면 `protected-files` 검사가 통과 | 훅이 명령 문자열에 `문서변경-승인`가 있으면 거부 | 문자열을 조합·인코딩하거나(예: 변수 결합) 스크립트 안에서 GitHub API를 부르면 훅이 못 봄. 같은 토큰이라 GitHub는 누가 붙였는지 구분 못 함 → **라벨 부착 이력(이슈 타임라인)과 병합 승인 창에서 사람이 확인** |
| Reviewer 승인 댓글 | `harness-review: APPROVED sha=...` 댓글을 Coordinator가 직접 쓰면 `review-gate` 통과 | 커밋 SHA에 묶여 있어 이후 커밋이 생기면 무효 | 같은 계정이 쓰므로 위조 방지 불가 → **PR 타임라인에서 Reviewer 호출 기록·판정 내용과 대조**, 병합 승인 창 |
| CI 설정 파일 변경 | `pull_request` 이벤트는 **PR 쪽의 워크플로 파일로 실행**된다. PR에서 `ci.yml`을 고쳐 `protected-files`나 `review-gate` 작업을 "항상 통과"로 바꾸면(작업 이름은 유지) 필수 검사가 초록불이 됨. 작업을 아예 지우면 필수 검사가 보고되지 않아 병합이 막힘 | `.github/workflows/**`는 로컬 L1·L2 보호 대상, 수정 시 `protected-files`가 감지(단, 고친 워크플로로 실행되면 감지 자체가 무력화될 수 있음) | **워크플로 파일을 바꾸는 PR은 사람이 diff를 직접 읽고 승인**. 강한 대안(`pull_request_target`로 기준 브랜치 워크플로 실행, CODEOWNERS + 2인 리뷰)은 1인·2주 규모에 과해 적용하지 않음 |
| 하네스 설정 파일 | `.claude/settings.json`·훅을 고쳐 장치를 끔 | L1 ask + L2 ask, CI `protected-files` | 위 CI 우회와 같은 원리 → 사람 확인 |
| 초기 push | `gh repo create --push`는 명령에 `git push`가 없어 훅의 "main 직접 push 금지"를 통과 | 저장소 생성 시 1회만 허용(사용자 승인 하에 수행) | 이후에는 ruleset이 서버에서 막음 |
| 가짜 성공 상태 | 커밋 상태 API(`repos/.../statuses/<sha>`)로 `protected-files` 같은 이름의 성공 상태를 직접 올리면 필수 검사가 통과될 수 있음 | ruleset의 필수 검사에 `integration_id: 15368`(GitHub Actions)을 지정 → **Actions가 보고한 결과만 인정** | 없음(서버 강제) |

**결론:** 하네스는 "실수와 무심한 우회"를 막는 장치다. 의도적인 우회는 같은 계정·같은 토큰을 쓰는 1인 구조에서 완전히 막을 수 없고, **사람의 병합 승인(L5)이 최종 관문**이다. 그래서 병합 승인 창에서 확인할 것: ① 보호 파일·워크플로 변경 여부 ② CI 결과 ③ Reviewer 판정이 실제 Reviewer 호출 결과와 일치하는지.

## 7. 알려진 한계 (발표·회고용)
1. 임의 스크립트를 통한 간접 파일 수정은 로컬에서 탐지 불가 → CI·브랜치 보호·사람 승인으로 보완.
2. Reviewer 승인 댓글은 같은 GitHub 계정으로 작성되므로 위조 방지가 아님 → 병합 승인 창에서 사람이 확인.
3. 대화형 세션에는 강제 비용 한도가 없음.
4. 1인 저장소에서는 GitHub의 "승인 리뷰 N개 필수"를 쓸 수 없음(작성자 본인은 자기 PR을 승인할 수 없음) → 필수 상태 검사(`review-gate`)로 대체.
5. 2026-11-25 작업 중 Coordinator가 Python 스크립트로 SPEC을 수정한 사례가 있음(당시 승인된 변경이었으나 L1을 거치지 않은 경로) — 이 문서의 L2·L3을 만든 계기.
